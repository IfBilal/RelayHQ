# Security measures (what each one defends)

| Measure | Where | Defends against |
|---|---|---|
| Row-level security on every tenant table, composite `(workspace_id, id)` FKs | `supabase/migrations/*`, tests in `supabase/tests/*` | One workspace reading or writing another's data (cross-tenant access, IDOR) |
| Workspace and actor derived from `auth.getUser()`, never from body/URL/JWT claim | `src/features/identity/server/session.ts`, `src/lib/api.ts` | Tenant/identity spoofing by editing a request |
| Writes only through `SECURITY DEFINER` functions in the non-exposed `private` schema, `search_path=''`, permission checked inside | migrations | Privilege escalation, search-path hijack, calling privileged RPC from the browser |
| Opportunity money lives in `private.opportunity_financials`, readable only via permission-gated functions; audit log records `{"changed": true}` only | migrations 2 and 6 | Value leak to users without `opportunity.value.view` (F1.4), including through the audit log |
| Append-only audit log (trigger blocks UPDATE/DELETE/TRUNCATE, no grants) | migration 1 | Tampering with history (F4.3) |
| Persisted deadlines + `pg_cron` + `FOR UPDATE SKIP LOCKED` + version checks | migration 3 | Lost/duplicated escalations, races between acknowledge and expiry |
| Zod validation on every server input | route handlers | Malformed or hostile payloads, mass assignment |
| Security headers (`next.config.ts`): CSP (`frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action` limited to self, with Stripe Checkout and Google sign-in pre-allowed for when those redirect flows ship (Chrome applies it to redirects after form posts), `connect-src` limited to self + Supabase), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, HSTS, `Permissions-Policy` | `next.config.ts` | Clickjacking, MIME sniffing, referrer leakage, protocol downgrade, unwanted device APIs; `connect-src` narrows where script can send data. Known limit: `script-src` keeps `'unsafe-inline'` because of Next's inline bootstrap, so the CSP only partially mitigates XSS (nonces would be the upgrade) |
| Cross-site write check on `/api/v1/*` (`Sec-Fetch-Site`, falling back to `Origin` vs `Host`) | `src/proxy.ts`, `src/lib/origin.ts`, `tests/unit/origin.test.ts` | CSRF against cookie-authenticated APIs. Exempt by design: signed webhooks (`/api/webhooks`, excluded from the proxy), cron route `/api/jobs` (outside `/api/v1`, bearer secret), anonymous public lead form (`/api/v1/public`, anon key only, no cookie session, rate-limited in the DB). Scope limit: only `/api/v1/*` route handlers are covered; today no cookie-authenticated mutating handler exists outside it (checked by grep), and Server Actions have Next's built-in origin check. New mutating routes must live under `/api/v1` |
| Cron route protected by a bearer secret compared in constant time | `src/app/api/jobs/dispatch-outbox/route.ts` | Unauthenticated triggering of the outbox, timing attacks on the secret |
| Public lead form rate limit in SQL (`private.hit_rate_limit`) | migration 3 | Spam and flooding of the anonymous endpoint |
| Login throttling | Supabase Auth (429 mapped to `rate_limited`) | Password guessing. No second app-level limiter: it would be in-memory on serverless and ineffective |
| Secrets only in server env, never `NEXT_PUBLIC_*`, never logged | `.env.example`, `CLAUDE.md` | Credential disclosure |
| Stripe webhook (`/api/webhooks/stripe`): raw-body HMAC-SHA256 signature with constant-time compare and a 5 min replay window, verified before any write; event id dedupe (`integration_events` unique key); amount/currency re-checked against the DB snapshot; applied by a service-role-only SQL function; rejected requests store a payload hash and reason only | `src/features/payments/server/*`, migration 13, `tests/unit/stripe-webhook.test.ts`, `supabase/tests/stripe_payments.test.sql` | Forged or altered payment confirmations, replay, double counting, a user or the browser redirect marking a payment paid. Tenant is derived from our own `payment_requests.checkout_session_id`, never from the payload |
| Payment amounts are kept out of audit and activity text; payment lists need `payment.create` or `opportunity.value.view` | migration 13 | Money disclosure to people without the value permission (F1.4) |
